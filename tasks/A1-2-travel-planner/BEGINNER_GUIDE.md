# 초보 개발자를 위한 A1-2 설명서

## 전체 흐름

```text
날짜 입력 → LLM이 JSON 추천 → 도시명을 지도 API에 전달 → 맛집 목록
         → 추천 JSON + 맛집 목록 → Markdown 리포트 → results/ 저장
```

`travel_planner.py`가 전체 순서를 관리하고, `providers.py`가 외부 API 통신을,
`grounding.py`가 최종 리포트의 가게 이름을 지도 검색 결과와 대조합니다.

## 1. REST API 요청과 응답

API는 다른 서비스에 정해진 형식으로 요청하고 응답을 받는 통로입니다. 요청에는 보통
주소(URL), HTTP 메서드, 인증 헤더, 검색 조건이나 본문이 들어갑니다. 응답은 상태 코드와
JSON 데이터로 옵니다.

- `GET`: 주로 데이터를 조회합니다. 이 프로젝트의 Kakao·Naver 맛집 검색이 예입니다.
- `POST`: 서버에 데이터를 보내 처리나 생성을 요청합니다. Gemini·OpenAI 호출이 예입니다.

`200`대는 성공, `401/403`은 키·권한 문제, `429`는 쿼터 초과, `500`대는 제공자 서버 문제로 봅니다.

## 2. LLM JSON이 다음 단계 입력이 되는 과정

자연어만 받으면 프로그램이 도시명과 날씨를 안정적으로 분리하기 어렵습니다. 그래서 LLM에
`recommended_cities`, `weather`, `events`, `reason` 키를 가진 JSON만 반환하라고 요청합니다.
프로그램은 JSON을 파싱하고 타입을 확인한 뒤 `recommended_cities`의 각 도시를
`제주 맛집` 같은 지도 API 검색어로 사용합니다.

즉, 첫 API의 **출력**이 두 번째 API의 **입력**이 됩니다. 이것이 여러 API를 파이프라인으로
연결한다는 뜻입니다.

## 3. 대표 오류와 대응

| 오류 | 뜻 | 이 프로그램의 대응 |
|---|---|---|
| 인증 `401/403` | 키가 틀렸거나 권한이 없음 | 다른 허용 제공자로 폴백, 모두 실패하면 오류 기록 |
| 쿼터 `429` | 호출 한도를 초과함 | 폴백하고 오류 기록; 같은 날짜는 캐시 사용 |
| 네트워크·`5xx` | 연결 또는 제공자 서버 문제 | 폴백; 장소 검색이 모두 실패해도 리포트 계속 생성 |
| JSON 파싱 | LLM 답이 약속한 JSON이 아님 | 요구를 단순화해 딱 한 번 재요청 |
| 검색 결과 0건 | 정상 응답이지만 장소가 없음 | 실패로 숨기지 않고 `데이터 없음`으로 계속 |

중요한 원칙은 실패를 무한 재시도하거나 감추지 않고, 복구 가능한 단계만 계속하며
`errors`에 원인을 남기는 것입니다.

## 4. API 키를 `.env`로 관리하는 이유

API 키는 서비스 비밀번호와 같습니다. 코드에 쓰면 GitHub 이력에 남아 다른 사람이 비용과
쿼터를 사용할 수 있습니다. `.env`는 로컬에서만 읽고 `.gitignore`로 공개를 막습니다.
`.env.example`에는 키 이름만 남겨 다른 사람이 필요한 설정을 알 수 있게 합니다.

이렇게 분리하면 키를 교체해도 코드를 고칠 필요가 없고 개발·배포 환경마다 다른 키를 쓸 수 있습니다.

## 5. `results/`가 원래 GitHub에서 안 보였던 이유

프로그램은 첫 실행 때 `results/`를 만들고 날짜별 JSON과 Markdown을 저장합니다. 원래는
`results/` 전체가 `.gitignore`에 있어 로컬에는 존재하지만 GitHub에는 올라가지 않았습니다.
지금은 새 실행 결과는 계속 무시하되, 키가 없는 검증된 예시 1쌍만 공개해 평가자가 결과 형식을
바로 확인할 수 있게 했습니다.
